## Correlated timestamp drift

A separate pacing defect can occur while prepared frames remain available. The clock used each new 16-refresh average directly to choose between a nominal display multiple and fractional deadlines. Firefox timestamps can drift across that short window: a local estimate around 8.53 ms temporarily resembles 117 Hz, even when the callback stream averages 120 Hz. That estimate can leave integer pacing and recreate one/three-refresh image intervals. A deterministic steady-120 Hz test with a gradually varying timestamp error reproduced 67 such violations in 20 seconds on version 34, without missing any callbacks or starving its producer.

The clock now damps small changes in the measured period, adopts large rate changes promptly, and clears its estimate after pause or a long stall. The same test produces zero cadence violations on both actual presenter bodies. Additional checks change the display between 60, 120, 90, 144, 240 and 60 Hz and verify settled delivery near 60 fps. ## Bounded texture-upload history

The texture cache previously tracked admission counts in an allocating hash table and cleared all entries after its 65,537th distinct key. That single update could release more than 65,000 nodes, and the next upload had to rebuild its admission history. A fixed 640 KiB table now tracks 65,536 keys in groups of four, checks at most four keys per admission and replaces one entry at capacity. It performs no per-upload allocations, frees or whole-table clears. History collisions can postpone caching an upload; cache reuse still requires the original full byte comparison, so the hint cannot alias different texture data.

An optimized Emscripten 6.0.11 standalone Wasm benchmark in Node processed 131,074 distinct keys per round with observed return values and allocator counters. Across three rounds, the old policy allocated 131,090 times, freed 131,089 times and cleared 131,074 entries in two batches. Its slowest individual updates took 1.05–1.38 ms and each round took 29.13–34.92 ms. The bounded policy allocated/freed zero times, took 0.062–0.070 ms at its slowest updates and 22.91–23.77 ms per round. ## Mapped uploads and Firefox display coordination

A fresh trace attributed rare long render continuations to GPU submission. Packet parsing in the sampled outliers took less than 0.15 ms; submission took 3–6.5 ms. A marker-only Firefox profile then captured `GPUQueue.writeBuffer` calls up to 10.04 ms, including small writes, without overlapping content-thread garbage-collection intervals. This is consistent with [Mozilla's tracked queue-write overhead](https://bugzilla.mozilla.org/show_bug.cgi?id=1968102), but does not establish the same internal cause for every observed gap.

Firefox compatibility now stages frame data and parameters in reusable mapped GPU buffers. Two GPU copies precede dependent compute commands in the existing command buffer. Remapping starts after submission and never blocks the render loop; unavailable buffers use normal queue writes. Allocations have a 16 MiB total buffer budget and a 2 MiB per-batch limit. Allocation/mapping failure disables this optional pool, and device loss disposes it. Chromium retains its original queue-write/encoder order and skips the inactive staging imports. The primary build keeps its existing upload path. Presenter-owned capacity wakes also apply to the staged Firefox compatibility path, with the existing audio guard.

An isolated alternating Firefox prototype compared 128 uploads per trial, with two trials per strategy and exact GPU readback. Aggregate main-thread work, including synchronous remap work, was 9.99 versus 1.68 ms at 64 KiB; 47.86 versus 5.01 ms at 512 KiB; and 118.30 versus 11.85 ms at 1,473,120 bytes. Wall durations remained approximately 1.6 seconds per trial because of GPU-completion round trips. These are transfer-strategy CPU measurements, not game FPS or power-consumption multipliers.

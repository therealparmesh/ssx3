## Coalesce readback progress on each buffer's owning queue

The worker readback helper previously remembered only the queue of the most recently requested GPU device. READ mappings of buffers from an earlier device therefore submitted progress work to the wrong queue. It also allocated one repeating progress timer per mapping, even when several mappings shared a device. The helper now records queue ownership when each buffer is created and shares one 1-ms/4-ms progress timer among that queue's pending READ maps. Completing one map leaves the others active; the final completion cancels the queue's timer. WRITE mappings retain their original promises and schedule no polls. Buffers created before installation retain the native mapping path rather than being polled on an unrelated device.

The expanded asset-free regression executes the production helper against independent device/queue objects. It covers concurrent same-device maps, multiple devices, exact optional argument forwarding, failed mapping/buffer creation, rejection, cancellation, stale callbacks, reentrant stop/map registration, unknown ownership and preservation of later prototype wrappers. The preceding source fails the one-timer assertion. All 21 JavaScript suites pass.

## Keep VU diagnostic counters out of ordinary interpretation

The decoded VU interpreter previously incremented one shared, non-atomic instruction total on every iteration, including when `PS2_VU_COUNT` was disabled. VU0 and VU1 can interpret on separate threads. A controlled concurrent fixture lost calls/totals in all five baseline trials; it retained the expected terminal registers. Counting is now conditional, and enabled counters use relaxed atomics. The original loop-increment placement and single-thread diagnostic output are preserved.

The new asset-free regression executes 10,000 programs on each VU concurrently, then another 20,000 after joining. It checks full terminal register state, quiet disabled diagnostics, unique call samples and the exact final instruction total. The preceding implementation fails this regression. All fourteen native suites pass with the correction.

A separate rotating-order benchmark used seven repetitions of NOP, arithmetic, integer-loop and flag-observing programs on both units. Baseline/candidate register and memory hashes matched in native and pthread Wasm builds, with main-thread suspension forbidden in the measured worker. Scalar-reference checks additionally covered NOP, integer-loop and flag-observing arithmetic; unobserved arithmetic used the existing optimized interpreter as its reference. These are small interpreter microbenchmarks, not a full-game FPS qualification or an attribution of the intermittent producer-starvation burst. The change removes unnecessary shared writes and a confirmed diagnostic-counter race. Browser gameplay, hosted timing and physical-device release gates remain open.

## Disc readiness and range preservation

A full disc cache could evict a requested ready chunk while scheduling speculative read-ahead. The readiness callback could consequently return true even though the next read would wait for HTTP. A multi-chunk read could also evict a later ready chunk before copying it. Readiness now reserves the complete demand range while allocating cache slots. Direct reads reserve the unread range and release already-copied chunks for reuse, allowing reads larger than the cache to complete. The cache remains bounded to 256 slots and speculative reads yield when no unreserved slot is available; fetch retry and dispatch behavior are unchanged.

The regression compiles the actual host cache implementation against a deterministic in-memory fetch completion. It reproduced readiness eviction with every other slot either ready or loading, and a refetch while copying a two-chunk cached range. The corrected code preserves those chunks and completes the cached reads without a fetch wait. The independent deferred-dispatch/retry/ownership regression also passes. This is a reproduced cache bug fix, not yet a demonstrated explanation for the live Chromium stall or a browser performance qualification of the rebuilt binary. A separate 300.782-second diagnostic of the preceding candidate averaged 60.002544 submissions/second, with no image/audio losses and a 23.45-ms maximum actual interval. ## Bounded texture-upload history

The texture cache previously tracked admission counts in an allocating hash table and cleared all entries after its 65,537th distinct key. That single update could release more than 65,000 nodes, and the next upload had to rebuild its admission history. A fixed 640 KiB table now tracks 65,536 keys in groups of four, checks at most four keys per admission and replaces one entry at capacity. It performs no per-upload allocations, frees or whole-table clears. History collisions can postpone caching an upload; cache reuse still requires the original full byte comparison, so the hint cannot alias different texture data.

An optimized Emscripten 6.0.11 standalone Wasm benchmark in Node processed 131,074 distinct keys per round with observed return values and allocator counters. Across three rounds, the old policy allocated 131,090 times, freed 131,089 times and cleared 131,074 entries in two batches.
